# 第二课：为什么需要“状态机”

> 这份课件已经准备好，但前台学习仍应在完成第一课的小练习后再进入这里。

## 1. 先把“状态”理解成流程所在的格子

这个项目当前有四个格子：

```text
人工核验中 → 人工已锁定 → AI 核验中 → AI 核验完成
```

程序只允许沿箭头往右走。比如人工还在核验时直接启动 AI，就属于不允许的跳步。

用代码表示这四个格子：

```python
class ReviewState(str, Enum):
    HUMAN_REVIEW_OPEN = "HUMAN_REVIEW_OPEN"
    HUMAN_REVIEW_LOCKED = "HUMAN_REVIEW_LOCKED"
    AI_REVIEW_RUNNING = "AI_REVIEW_RUNNING"
    AI_REVIEW_COMPLETE = "AI_REVIEW_COMPLETE"
```

`Enum` 可以理解为“只能从规定答案中选一个”，避免把状态误写成任意字符串。

## 2. 为什么不是只做一个“提交”按钮？

按钮只是页面上的外观。真正的规则必须在后端代码中执行，否则有人可以绕过页面直接调用接口。

锁定前，系统检查：

- 任务的预期参数清单是否非空且没有重复 ID；
- 每一个预期参数是否都有人工结论；
- `DIFFERENT` 和 `UNABLE_TO_JUDGE` 是否写了原因。

少一个参数，锁定操作整体失败，任务仍停留在 `HUMAN_REVIEW_OPEN`。这叫“原子性”：不能出现一半成功、一半失败的状态。

## 3. 锁定以后为什么不能再改？

如果人工先提交，看到 AI 结果后又能静默修改原判断，我们就无法回答：

```text
人工第一次独立判断到底是什么？
```

所以 `record_human_decision()` 只在 `HUMAN_REVIEW_OPEN` 状态有效。锁定后的更正将来要走单独的追加记录流程，保留原值、修改人、修改时间和原因，而不是覆盖旧记录。

## 4. 仅仅把 AI 结果藏在页面上够不够？

不够。AI 还可能通过这些侧面泄露答案：

- 高亮颜色；
- 参数排序；
- “发现 3 个异常”的计数；
- AI 进度条；
- 浏览器接口返回的数据；
- 缓存或日志中的结果。

因此当前默认采用最严格、也最容易解释的方式：人工锁定前根本不启动 AI。并且在 AI 全部完成前，公开读取方法也拒绝返回部分结果。

## 5. 这一阶段你需要记住什么？

1. 状态机规定流程可以怎样移动；
2. 页面按钮不是安全边界，规则要由后端执行；
3. 全部字段完成后才能原子锁定；
4. 锁定后的人工原判断不能被覆盖；
5. AI 在人工锁定前既不能运行，也不能被读取。

这些规则比选择哪一种 LLM 更重要，因为模型会更换，但流程约束必须稳定。
