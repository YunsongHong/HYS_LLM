## 1. 规范性边界

本文中“应/SHALL”表示 **ParamGuard Vision 项目需求**，不表示每一条都是法规原文。其中 human-first 的必须顺序主要溯源至 `PD-HF-01`：它是为满足面试题设中的“人工须先独立完成”约束而制定的项目风险控制。

官方来源提供的是更上位的设计依据，例如可追溯 URS、风险管理、授权访问、步骤顺序检查、准确性复核、审计轨迹、变更控制和测试证据。特别是，现行 Annex 11 不规定“人工必须在 AI 之前”；请勿把下表的 `PD-HF-01` 需求写成普遍法律要求。

## 2. 角色和术语

- **R1**：第一审核员，必须先独立查看原始证据并作答。
- **定向异常复核**：在 R1 锁定且 AI 完成后，只处理服务端从冻结事实重算出的异常字段。它匹配面试题设，但不自动具有“独立盲二审”的身份分离含义。
- **R2**：全字段独立盲二审员；仅当已批准的 SOP/风险 profile 选择该路径时使用，与 R1 不得为同一身份。
- **流程 profile**：服务端信任、带版本和内容哈希的锁后分流规则；客户端和 AI 不能自由指定。
- **QA/仲裁员**：处理字段结构错误、未解决分歧和流程异常；在 PoC 中也不构成真实放行。
- **锁定**：在服务端原子检查“全部预期参数已作答”后，将 R1 结论转为不可覆盖的原始记录。
- **AI 线索**：OCR 文本、置信度、AI 判断、运行状态、风险颜色、排序、计数、缓存键、响应大小/时间或任何能让 R1 推断 AI 结果的元数据。
- **完成不等于放行**：任务流程完成只表示 PoC 规定的步骤已执行，不代表产品、批次、设备或偏差已被放行。

## 4. 密封并行的禁用条款

当前基线不允许在 R1 锁定前运行 AI。未来若要新增“后台计算、前台密封”模式，必须先同时满足：

1. 实际适用 SOP 明确允许后台并行；
2. 记录化风险评估和 Process Owner/QA/IT/OT Security 审批；
3. 独立的密封数据库/权限边界，R1 不能通过任何直接或侧信道推断结果；
4. 包含 UI、API、WebSocket、日志、缓存、队列、排序、时延、长度和错误差异的侧信道对抗测试；
5. 受控变更、独立复审和回退计划。

缺任一项时，系统必须保持严格顺序。

## 5. 验证和追溯出口准则

本 URS 不因为已编写就视为实现完成。每一条 `Must` 在里程碑结束时都应具有：

- 指向设计/代码的双向追溯；
- 至少一个正向验证和一个相关负向/对抗验证；
- 固定版本的测试输入、预期结果、实际结果、环境和时间；
- 未解决偏差、限制和残余风险；
- 与实际 intended use 相称的独立只读复审。

“自动化测试通过”只是工程证据，不是 GxP 验证、Part 11 认证或监管批准。
